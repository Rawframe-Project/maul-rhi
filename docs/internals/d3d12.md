# The Direct3D 12 driver

How the D3D12 driver (`driver_d3d12.c`, `d3d12_*.c`) meets the SPI. It is the native driver of Windows builds. It is C over the COM interfaces' C form (`COBJMACROS`), against the DirectX headers kept as published in `directx/` and the Windows SDK's DXGI headers.

## Runtime and adapters

The driver opens `d3d12.dll` and `dxgi.dll` from the system directory when an instance starts; without them, or without a DXGI factory, the instance has no adapters. It uses whatever D3D12 runtime its process has (the system's, or the Agility SDK the program's executable selects) and never selects one itself, since the choice belongs to the executable. A search lists every DXGI adapter that opens a feature level 12_0 device with shader model 6.0, WARP among them as a software adapter, under its LUID. Opening a device there to read its facts is cheap, since D3D12 keeps one device per adapter while it is held.

Limits are WebGPU's floor, raised where every device at the floor goes further: 2D textures of 16384, 2048 layers, a 128-byte root block within the root signature's 64 words. Every device grants timestamps, BC textures, 32-bit float filtering, `rg11b10ufloat` targets, dual-source blending, unclipped depth and indirect first instances, which feature level 12_0 requires; 64-bit integers and wave operations where D3D12 reports them; heaps on resource binding tier 3. A device holds its D3D12 device and three command queues: the direct queue, which presents, and a compute and a copy queue beside it.

## Objects

Buffers, textures, views, samplers and query sets sit in tables in the device's block, a handle being a slot plus one. Buffers and textures are committed resources in the default heap, starting in the common state.

- A buffer's size rounds up to 256 bytes, so that a uniform binding's constant buffer view stays inside it.
- A texture whose views change its format, or a depth texture, is made in its typeless family.
- A view's slot holds, in a CPU-only descriptor heap, a shader resource view where it is sampled and an unordered access view of its first mip where it is stored to; bindings copy them to the GPU's heaps.
- A 2D or cube view of a later layer is a one-layer or one-cube array, since only arrays name their first layer. A stencil view reads the second plane.

## Pipelines

A shader keeps a copy of each entry's DXIL and makes one root signature (version 1.1) for every pipeline of the container: root constants for the root block, the constants (in rows of four, as their buffer declares them) and the vertex information where the container has them, then per table a descriptor table of its resources and one of its samplers, each binding a one-descriptor range at the register and space the D3D12 map gives, visible to every stage, data volatile. A container whose root signature passes 64 words is refused as unsupported.

A pipeline state is made at the call and answered at the next poll. It holds a reference on the root signature, a copy of the bindings and its constants' words (each constant's default unless given), so it outlives its shader; a fixed constant given another value is refused. Vertex attributes are the `TEXCOORD` semantic of their location, as SPIRV-Cross names vertex inputs; alpha blend factors read alpha, and minimum and maximum blending use factors of one.

D3D12's vertex and instance ids leave out the first vertex and instance. A pipeline whose vertex entry reads them takes them as root constants: set before a direct draw, and for an indirect one copied ahead of its arguments into the slot's scratch buffer, where the pipeline's command signature sets them. Counted multi-draw is `ExecuteIndirect` with a count buffer; for pipelines that read their first vertex or instance, a compute pass of the library's (`src/d3d12_expand.hlsl`, compiled offline into `src/generated/d3d12_expand.h` by `tools/gen_kernels.py`) first expands the records. Multiview is view instancing, four views.

## Frames

Three frames run at once. Each slot holds a command allocator and lists for each queue, an upload buffer for its staging (which stays in the generic read state), and CPU-only heaps of render target and depth stencil views for its passes' targets. One readback buffer, which stays in the copy destination state, takes every readback at its offset in the ring, and each finished frame copies its readbacks' ranges out. Frames signal one fence with their serial, so a poll reads one value. A removed device reads all ones there, and its removal reason becomes the loss report's reason and message.

A frame is recorded whole before any of it runs, so a frame that fails to record runs nothing. A frame that fails once part of it is queued, as when a queue refuses a wait or a signal, waits for every queue to finish what it holds, through a last signal of each lane's fence, before its lists and transients are released; a queue that takes no signal, as on a removed device, is not waited for. Its transients are made at its submit and released when it finishes ([memory.md](memory.md#gpu-memory-per-driver)). A barrier marked aliasing is led by an aliasing barrier, and a placed render target or depth texture is discarded whole at its first use, as D3D12 requires before anything else touches it.

## Queues

The frame's passes run on three lanes, one per queue, each with a fence of its own (`d3d12_lanes.c`). A pass runs on its class's queue when that queue's lists can record it, and on a queue that takes more otherwise, since the class is a hint:

- **The copy queue** takes a transfer pass that touches only buffers and has no aliasing barrier. A copy list moves resources only between the common and copy states, and a texture used on a copy queue decays to the common state after it, which the plan's states do not follow.
- **The compute queue** takes an async compute pass, or a transfer pass the copy queue does not, whose textures are used and moved only in states a compute list takes: the common, unordered access, non-pixel shader resource and copy states. A sampled texture's state includes the pixel shader's, so an async compute pass that samples a texture, or that finds one in a target or shader-read state left by graphics work, runs on the direct queue.
- **The direct queue** takes the rest, native passes included.

A pass follows the passes its `waitFor` names and, so that a class keeps its order when its passes run on different queues, the pass of its class before it. A lane's passes go in the frame's order into batches: a new batch where a pass follows a pass on another lane, and the batch ends after a pass another lane follows. Each batch waits on the other lanes' fences for the batches its first pass follows, runs its lists, and signals its lane's fence. Batches run in the order they open, the frame's order of their first passes, so every wait names a signal already queued. The compute and copy lanes' first batch of a frame waits on the frame fence for the frame before, which orders it after that frame's end barriers and present; this serializes a little at the frame's start. With work beyond the direct queue, the frame's end is a last batch on the direct queue that waits for every lane's last; a frame of direct work only is one batch, recorded and run as with one queue. Before anything runs, an assertion works the required waits out again from the frame view and checks the batches hold them.

On the compute and copy queues, buffers take only the read states those lists name: a storage read is the non-pixel shader resource state, a sealed buffer's reads leave out the pixel shader and index buffer states, and the copy queue moves buffers only between the copy states.

## Barriers and buffer states

This is where D3D12 differs most from the core's model.

- **Textures** move, per subresource, between the classic states the plan's states map to; a transition between two unordered access uses is a UAV barrier.
- **Buffers are the driver's to track.** D3D12's read states gather several reads into one, which the plan's states do not, so each copy, binding and pass that declares a buffer moves it to the state it needs, gathering read states, and a plan's barrier on a buffer between two reads does nothing. An imported sealed buffer starts the frame in every read the sealed state allows. A plan's barrier after a write on a buffer in the unordered access state is a UAV barrier.
- Every buffer starts each batch in the common state, which D3D12 decays buffers to when a command list finishes, and the driver tracks its state on each lane apart.
- The buffers a bind point's tables, vertex and index buffers use move to the states they need at each draw or dispatch.

A copy with a buffer offset off D3D12's 512-byte placement is split into one copy per row of blocks. Clears are the targets' loads; discarding loads and stores keep the contents. A pass's multisampled targets resolve at its end. `mrhiClearBuffer` copies from a device-owned 64 KiB buffer of zeros (D3D12 zeroes committed resources), one copy per 64 KiB; query resolves of unwritten queries copy from the same buffer.

## Bindings and heaps

Each slot has shader-visible heaps of resource and sampler descriptors: the program's heaps' regions first, then rings of as many resource descriptors as the frame's commands record (each binding is one) and of samplers up to what D3D12's 2048 leave. A table writes its descriptors there together (a uniform buffer as a constant buffer view, a storage buffer as a raw unordered access view, a read-only one as a raw shader resource view, a texture as a view of the binding's shape) and sets them as its descriptor tables. A table of the samplers the last one wrote takes those again. Pipelines of one container share a root signature, so their tables and root block stay set between them; each pass sets its own.

**Heaps** are granted on resource binding tier 3, which lets tables hold unread descriptors uninitialized, with `heapSize` 65536 and `samplerHeapSize` 256, since the heaps and the frames' rings share the 2048 shader-visible samplers a list binds. A device whose heaps would leave the rings fewer than 64 descriptors of a kind is refused. Every frame slot's shader-visible heaps hold each heap's regions at the front, at the heap's slot, and an entry is written into every slot's region. A storage buffer entry is a raw unordered access view when shaders may write it, else a raw shader resource view, so a shader reads a buffer entry through a declaration of the same writability. A root signature of a container reading heaps adds an unbounded table per range class, pointed at the pass's heap after each pipeline.

## Queries

An occlusion query set is a query heap; occlusion queries are binary. A resolve copies the queries the frame wrote and zeros for the others. Pipeline statistics write D3D12's eleven counters, which resolve straight into the program's buffer.

## Surfaces

A surface is a Win32 window, and every adapter presents there, DXGI's compositor taking another adapter's images. The caps offer 8-bit and 10-bit unorm in sRGB, half floats in scRGB, and HDR10 where the window's monitor is in HDR; fifo, mailbox, and immediate where DXGI tears; opaque alpha only, since only composition swapchains blend.

A configured surface is a flip-discard swapchain of three images on the device's queue, its color space set from the color, Alt+Enter turned off, its images stretched to the window, so the window's size never refuses one. A window holds one swapchain at a time, so configuring again and unconfiguring wait for the device's frames and release the old swapchain at once. Acquiring waits on the frame latency waitable object (two presents queued at most, a second at most), so presenting never blocks; it answers occluded for a minimized window and suboptimal for a window whose size is no longer the swapchain's. A frame presents its images after its work, at sync interval 1 for fifo and 0 otherwise, tearing for immediate.

## Native passes

`mrhiSetD3d12PassCommands` takes a closed direct command list. The driver records its own lists one after another on its allocator and runs each list, its own and the program's, in its own `ExecuteCommandLists`, after which D3D12 has finished the earlier work and buffers have decayed to the common state. So a native pass finds its textures in their accesses' states and its buffers in the common state, and the driver tracks its buffers from the common state again after it. The list it records into after a native pass has no root signature set, so the next pipeline sets its own again, even one of the container set before.

## Debugging

CI runs the conformance suite and the samples on the hosted runner's WARP under the Agility SDK's debug layer and GPU-based validation, which the tests' executables select by exporting `D3D12SDKVersion` and `D3D12SDKPath` (`test/d3d12_debug.c`); any error the layer reports fails the test. Pull requests run the validation without its resource state tracking, which reports false errors ([#7](https://github.com/Rawframe-Project/maul-rhi/issues/7)); a nightly cell runs it whole.
